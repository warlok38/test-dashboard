# Индикатор первоначальной загрузки приложения

## Цель

Заменить текущий спиннер и текст «Загрузка приложения...» на спокойный двухэтапный индикатор без процентов. Индикатор должен объяснять длительное ожидание на слабой сети, но не появляться при быстрой загрузке и не создавать коротких миганий между гидратацией React и авторизацией.

## Пользовательский сценарий

1. Сервер отдаёт HTML с этапом «Загружаем интерфейс...».
2. Первые 500 мс индикатор скрыт.
3. Если приложение ещё не готово, индикатор плавно появляется вместе с progress-линией.
4. После гидратации запускается существующая авторизация.
5. Если авторизация продолжается более 500 мс, подпись меняется на «Проверяем доступ...».
6. Если авторизация завершается быстрее, второй этап не показывается.
7. При готовности progress-линия завершается, индикатор плавно исчезает, а приложение становится доступно.

Загрузка данных дашборда остаётся внутри существующих skeleton-компонентов и не включается в глобальный индикатор.

## Размещение

Изменение остаётся внутри существующего слайса `features/auth`:

```text
src/features/auth/
└─ ui/
   ├─ AuthContentGate.tsx
   ├─ AuthLoadingIndicator.tsx
   └─ AuthLoadingIndicator.module.css
```

`AuthLoadingIndicator` не выносится в `shared/ui`, поскольку его этапы и поведение связаны с конкретным процессом запуска и авторизации приложения. Публичный экспорт компонента не требуется, если он используется только внутри `AuthContentGate`.

## Состояния и поток данных

`AuthContentGate` продолжает использовать существующие поля Redux:

- `isInitialized` — инициализация авторизации завершена;
- `isInitializing` — запрос авторизации выполняется;
- `isAuthorized` — доступ к защищённому содержимому разрешён.

Новые поля Redux не добавляются. Задержка переключения подписи является локальным визуальным состоянием `AuthLoadingIndicator`.

Начальный серверный рендер всегда использует этап `interface`. Для второго этапа `AuthContentGate` вычисляет признак проверки доступа: авторизация выполняется либо защищённое содержимое остаётся заблокированным до редиректа на статусную страницу. Когда проверка доступа начинается, компонент запускает таймер на 500 мс. Если приложение становится готово или переходит на статусную страницу до срабатывания таймера, таймер очищается и этап `auth` не показывается. Если таймер сработал, подпись меняется на «Проверяем доступ...».

Для плавного завершения `AuthContentGate` сохраняет локальное состояние показа индикатора ещё на 150–200 мс после готовности. В это время линия получает завершающий CSS-класс, доходит до конца и исчезает. После этого отображается разрешённое содержимое или статусная страница.

## Progress-линия

Линия реализуется CSS-анимацией без численного процента:

- весь индикатор получает задержку появления 500 мс;
- появление выполняется через короткое изменение прозрачности;
- заполнение быстро проходит начальную часть, затем замедляется и приближается к 85–90%;
- при длительном ожидании линия остаётся около конца с лёгкой ненавязчивой анимацией;
- при завершении линия быстро доходит до конца, после чего индикатор исчезает за 150–200 мс.

CSS-задержка обязательна для первого этапа: до гидратации React таймеры компонента ещё не выполняются. JavaScript управляет только задержанным вторым этапом и состоянием завершения.

## Обработка ошибок

Существующий поток ошибок авторизации и редиректы на страницы запрета доступа или ошибки не меняются. При ошибке индикатор продолжает закрывать защищённое содержимое до перехода на соответствующую статусную страницу. После перехода он завершает анимацию и освобождает содержимое страницы. Дальнейшее поведение определяется текущей логикой `AuthRedirectWatcher` и `AuthContentGate`.

## Проверка

- При загрузке быстрее 500 мс индикатор не появляется.
- При медленной загрузке до гидратации виден этап «Загружаем интерфейс...».
- Быстрая авторизация не вызывает мигание текста «Проверяем доступ...».
- Авторизация дольше 500 мс переключает подпись на «Проверяем доступ...».
- Успешная авторизация плавно завершает индикатор и показывает приложение.
- Ошибка авторизации сохраняет существующий редирект и экран ошибки.
- Поведение проверяется в production-режиме через `npm.cmd run build` и `npm.cmd start`; показатели `next dev` не используются как оценка размера и скорости production-бандла.
- После изменений выполняются `npm.cmd run lint` и `npm.cmd run build`.

## Вне области изменений

- Измерение реального процента загрузки JS-чанков.
- Отображение технических этапов `main-app.js`, `layout.js` и `page.js`.
- Изменение API авторизации или Redux-модели.
- Изменение skeleton-компонентов загрузки данных дашборда.
